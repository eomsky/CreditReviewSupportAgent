# 테스트 하네스 설계 기준

## 사용자 합의

최종 산출물 기준은 올바르게 첨부된 반도체 기업 심사보고서 13쪽이다. 잘못 첨부된 재무표 ZIP과 골프장 이미지는 기준에서 제외한다. 보고서 이미지에 있는 수치와 결론은 테스트 입력의 사실로 복제하지 않는다.

분석 단위는 provisional F01~F30. 각 요인이 근거 수집 → 의미 해석 → 유연한 표 구성 → Python 계산 → 판단 → 검증/보완을 거친다. 종합 단계는 요인 간 관계와 상충을 다룬다. 요인 목록과 최종 보고서 목차는 동일할 필요가 없다.

LLM은 단순 계산 입력값 추출기에 한정되지 않는다. 자료를 보고 표의 열·행·자료형을 구성하고, 계산 목적·입력 매핑·Python 코드를 만든다. Python은 DataFrame을 생성하고 코드를 실행한다. LLM은 결과를 해석하며 필요한 경우 같은 PDF를 다시 조회한다.

단계 간 공통 JSON 계약은 일정하게 유지하고, 데이터셋과 분석 내용은 유연하게 생성한다. 원문·생성 데이터·계산 결과·판단 요약은 서로 다른 산출물로 기록한다. 내부 사고 전문 대신 근거, 작업 이유, 계산 및 판단 요약을 남긴다.

## 실행 구조

`Harness.step(F24)`는 한 번의 LLM action을 수행한다. `search`, `read`, `dataset`, `calculate`, `conclude` action을 JSON schema로 검증한다. 원문 공표일은 review_date 이전이어야 한다. 출처를 확인하지 않은 셀, 불명확한 연결/별도 데이터는 계산에 넘기지 않는다.

action의 `reason`은 검토 가능한 짧은 작업 설명이다. `conclude.requirements`는 요인별 근거요건과 source ID의 매핑이며 coverage는 이 매핑에서 계산한다. LLM이 매핑한 근거의 의미적 적합성은 별도 검토가 필요하다. coverage가 100%라고 해서 심사 승인 또는 보고서 검증 통과를 뜻하지 않는다.

UI는 state.json을 읽는 같은 Python 상태를 사용한다. immutable artifact JSON과 events.jsonl은 입력·응답·실행·오류를 보존한다. 요인 재시작은 판단을 비우고 기존 근거·데이터·계산을 재사용한다. 최종 보고서 참조를 무효화하지만 과거 보고서 파일은 보존한다.

## 기존 기능 연결

기존 SemanticPromptTransfer의 추출 블록을 `documents.from_spt_blocks`로 연결할 수 있다. 구조가 풍부한 결과는 Source JSON으로 직접 등록하여 부모/자식 참조와 metadata를 보존한다. 간소화된 신규 PDF 파서로 기존 구조 추출 기능 전체를 대체한다고 보지 않는다.

기존 CreditReasoningLayer, prompt budget, claim verification 및 evidence capture는 다음 통합 대상이다. 이번 저장소에는 운영 런처·HTML·기존 엔진을 복제하지 않았다. 운영 자산은 Drive에 그대로 둔다.

## 현재 구현과 후속 과제 구분

구현: 단계 계약, 동적 데이터셋, Docker 계산, 요인별 반복 액션, 기본 복합 검색, 날짜 차단, 참조 검증, 기록/재개/요인 재시작, 최소 화면, 초안.

후속: 기존 엔진 실연결, 토크나이저 기반 예산, 대형 문서 영구 색인, OCR/연속표 QA, 학습형 reranker, 웹/Drive/내부 DB 연결, 독립적인 의미·수치 검증, 자료 변경의 의존성 기반 재분석, 완전한 30요인 실제 사례 평가.

파일·코드가 존재한다는 사실과 실제 모델을 연결해 품질 검증을 완료했다는 사실은 구분하여 보고한다.
